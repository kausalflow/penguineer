The plant graph¶

The plant context graph lives in its own small package, plantgraph, which depends only on Pydantic. penguineer and homeostat both import it, so a real plant and a simulated one are described by the same types.

Every node and edge carries a stable id, a provenance (declared, inferred or confirmed), a source (user, llm, data, dexpi or homeostat), a confidence between 0 and 1, and valid_from and valid_to dates. graph.valid_on(day) gives the plant as it was on that day.

Nodes¶

Type What it represents Key fields
unit The scope of one project name
equipment Vessels, exchangers, columns, pumps kind, holdup_m3
stream A material flow between equipment phase
tag One historian signal tag, unit_of_measure, range_low, range_high, role
loop A control loop pv, sp, op, mode (IDs of tag nodes)
actuator A valve or drive a loop moves kind
sample_point Where a lab sample is taken
quality A LIMS property with a spec property, spec_low, spec_high

A tag's role is measurement, setpoint, output, mode or setting. Setpoints, modes and settings may sit still for days, so data health never reports them as frozen.

Edges¶

Type From → to Key fields
flows_to equipment or stream → equipment or stream dead_time_min with an interval, recycle
measures tag → equipment or stream measured_variable
controls loop → actuator acting
manipulates actuator → equipment or stream
samples sample point → equipment or stream
reported_as sample point → quality
affects any → any a cause link an engineer asserts

In YAML¶

schema_version: 1
unit: demo-reactor
nodes:
  - {id: R-101, type: equipment, kind: vessel, holdup_m3: 12.0}
  - {id: TI-101, type: tag, tag: TI-101.PV, unit_of_measure: degC, range_low: 0, range_high: 300}
edges:
  - {id: m1, type: measures, from: TI-101, to: R-101, measured_variable: temperature}

Checking a graph¶

penguineer graph check --graph graph.yaml validates the schema and these plant rules: unique IDs, no edges to unknown nodes, edge endpoints of the right types, every loop with a PV and an OP, flows_to cycles only through an edge flagged as recycle, and every quality reachable from a sample point on the plant. It then lists the confirm queue: inferred edges, sorted by how many qualities depend on them. It exits with 1 when there are errors.

Drafting a graph from a tag list¶

penguineer graph draft writes a first graph.yaml from the historian's tag list, so that an engineer starts by confirming a draft rather than typing every node.

penguineer graph draft --tags tags.csv
penguineer graph check --graph graph.yaml

The tag list is a CSV with a tag column and, if the export has them, description, unit, equipment, range_low and range_high (common alternatives such as TagName, UOM or Max are recognized).

graph draft: 14 tags, 2 loops, 2 valves, 2 equipment; 5 edges (0 flows_to), all inferred
wrote graph.yaml
1 tags without an ISA-5.1 name: GRADE
warning: TT-305: the name says temperature but the unit 'bar' is a pressure
note: no piping (flows_to) in a tag list: add it, give the P&ID with --pid, or confirm what the LLM proposes
next: penguineer graph check --graph graph.yaml

The draft reads each name with ISA-5.1 conventions:

Part Example Read as
First letter FIC-102, TT-301, PDI-5 The measured variable: flow, temperature, pressure, level (L), analysis (A), ...
Modifier PDI-5, FQI-7 Differential, totalized or ratio
Function letters FIC-102, FT-102, FV-102 Controller, transmitter, indicator, valve, ...
Number FIC-102 The loop: FIC-102, FT-102 and FV-102 belong together
Prefix 11FIC1001, U1.TI101 A plant or area code, kept as part of the loop
Suffix FIC-102.SP, TIC-301.out The signal: PV, SP, OP (or OUT, MV), MODE

From that it drafts:

  • a tag node for every tag, with its role (measurement, setpoint, output, mode);
  • a loop for every group with a controller (letter C) or a setpoint or output signal: its PV is the controller's own measurement, else the group's transmitter or indicator;
  • the actuator each loop drives, from the group's valve tag (FV-102) or named by convention, with a controls edge;
  • equipment from the equipment column, or from equipment IDs in the descriptions ("Reactor R-101 temperature" gives R-101, a reactor), with a measures edge from the tag.

Every drafted node and edge is inferred, with a confidence (lower when it comes from a description or a naming convention than from a column or a tag in the list), so all of them appear in graph check's confirm queue. A unit that contradicts the name is reported. Tags without an ISA-5.1 name, such as GRADE, become tag nodes without a role.

A tag list does not say how material flows, so on its own the draft has no flows_to edges and no streams. Sample points and qualities come from the engineer.

Adding the P&ID¶

With a DEXPI P&ID (the Proteus XML that P&ID tools export), the draft also reads how the plant is piped and where its instruments sit:

penguineer graph draft --tags tags.csv --pid pid.xml

graph draft: 13 tags, 2 loops, 2 valves, 3 equipment; 19 edges (9 flows_to), all inferred
wrote graph.yaml
1 tags without an ISA-5.1 name: GRADE
warning: P&ID instrument PI-305 has no tag in the tag list
next: penguineer graph check --graph graph.yaml

From the P&ID it drafts:

  • equipment for every piece of equipment, by its tag name, with its kind from the DEXPI class (TubularHeatExchanger is an exchanger);
  • a stream for every off-page connector: a feed where material comes in, a product where it leaves;
  • a flows_to edge wherever a pipe runs from one piece of equipment (or a feed) to the next, through tees, reducers and valves, in the direction the P&ID draws its connections;
  • for each instrument function that matches the tag list by letter and number (TIC-201 on the P&ID is TIC-201.SP, TT-201 and the rest in the list; a plant prefix is ignored): a measures edge from its sensor's tag to where the sensor sits, and, for a controller, the valve its signal goes to as the loop's actuator, with a manipulates edge to the equipment that valve's pipe feeds.

A sensor on a nozzle measures that equipment (confidence 0.85). A sensor on a pipe is read as measuring the equipment the pipe comes from, and a valve on a pipe as acting on the equipment it goes to (0.6): confirm those. When the tag list says otherwise and is more sure (its equipment column, or a valve tag in the list), the tag list's answer is kept and the difference is reported. Instruments on the P&ID without a tag in the list are reported too. Everything from the P&ID has source: dexpi and is inferred, like the rest of the draft.

Asking an LLM for the rest¶

What the rules and the P&ID leave open, an LLM can propose: which equipment a tag measures when its description names none, what a valve acts on, and, without a P&ID, the piping.

penguineer graph draft --tags tags.csv --llm local --llm-model <model>

graph draft: 7 tags, 1 loops, 1 valves, 2 equipment; 6 edges (1 flows_to), all inferred
wrote graph.yaml
1 tags without an ISA-5.1 name: GRADE
note: the LLM proposed 4 relations; 3 kept (source llm), 1 rejected
note: rejected LLM proposal R-101 -flows_to-> E-201: would close a cycle
next: penguineer graph check --graph graph.yaml

The LLM sees the plant's equipment, streams and valves, the relations already drafted, and the open tags with their names, units and descriptions; never any data. It may only link nodes that exist. A proposal is kept only if both ends have the right types, it places a tag or valve that was open (it never changes a drafted relation), it does not repeat an edge, and its piping closes no cycle; the summary lists every rejected one and why. Kept edges have source: llm, are inferred, and get a confidence of 0.3 to 0.5, below every rule-based edge. --llm-dry-run writes the requests to llm-request.json next to the graph and sends nothing. See Using an LLM for choosing a model.
